# Выпуск релиза: что нужно подготовить

Документ для того, кто садится выпускать версию. Основная версия — в
[README](README.md#выпуск-версии), здесь чек-лист и то, что настроить
на стороне GitHub один раз.

Репозиторий публичный, значит первое, что делает человек, — открывает
страницу и качает файл. Поэтому «красивая страница» и «правильно
приложенный .exe» здесь важнее, чем строгость описаний.

---

## 1. Один раз для репозитория

**Описание и темы** (Settings → General → Description):
описание в одну строку видно в поиске GitHub и в карточке репозитория.
Темы (topics) — то, по чему находят: `kanban`, `task-manager`,
`self-hosted`, `offline`, `flask`, `sqlite`, `windows`, `tray`,
`python`, `retro`.

**Issues** — включить. Шаблоны (`.github/ISSUE_TEMPLATE/`) завести
только если будут чужие баги; для одного разработчика часто лишнее.
Discussions — по желанию, обычно не нужно.

**README должен начинаться со скачивания.** Сделано: в начале есть раздел
«Скачать» с прямой ссылкой на `releases/latest/download/QuestLog.exe`,
а запуск из исходников идёт следом в разделе «Установка и запуск».
Ссылка ведёт на последний релиз, поэтому номер версии в README
обновлять не нужно.

**Сборка релиза автоматическая.** `.github/workflows/release.yml` по
тегу `v*` гоняет тесты, собирает `.exe` на `windows-latest`, считает
SHA-256 и публикует релиз с файлом и текстом. Правило применяет
`python release.py 1.0.1` — скрипт сам поднимает `VERSION`, собирает,
считает хеш, ставит тег и создаёт релиз через GitHub API; без токена он
дотолкнёт тег, и релиз опубликует CI.

**Защита ветки.** `python scripts/setup_ruleset.py` с токеном
администратора ставит ruleset: force push в `master` запрещён, слияние
требует зелёной проверки «Проверки / tests». Руками то же самое —
Settings → Rules → Rulesets.

**LICENSE** — MIT, файл в репозитории есть и отслеживается. Для
публичного репозитория это всё, что нужно, чтобы им можно было
пользоваться.

**Dependabot** (Settings → Dependabot alerts) — включить: для
публичного проекта с зависимостями это бесплатное обновление безопасности.

## 2. Перед каждым релизом

### 2.0. Короткий путь

```
python release.py 1.0.1          # всё сразу: версия, тесты, сборка, хеш, тег, релиз
python release.py --bump patch   # 1.0.0 -> 1.0.1
python release.py --dry-run      # показать план, ничего не делая
```

Требуется чистое рабочее дерево: релиз собирается из того, что лежит в
git, а не из недописанного кода. Всё остальное в этом разделе — то, что
скрипт делает сам; список нужен, чтобы понимать, что происходит, и
чтобы выпустить версию руками, если CI недоступен.

### 2.1. Версия

1. Поднять номер в файле `VERSION` (`1.0.0` → `1.0.1`). Это единственный
   источник номера: из него подвал в приложении, ответ `/api/health` и
   сравнение с последним релизом.
2. Тег релиза должен быть ровно `v` + этот же номер: `v1.0.1`.
   Приложение срезает `v` и сравнивает цифры (`version_tuple` в
   [server.py](server.py)), поэтому расхождение не сломает проверку, но
   сделает подсказку обновления бессмысленной.

### 2.2. Проверки перед сборкой

3. `.venv/Scripts/python.exe -m pytest -q` — все тесты зелёные.
4. `.venv/Scripts/python.exe check_js.py` — синтаксис всех модулей JS.
5. Рабочее дерево чистое: `git status --short`. Ничего изменённого
   от релиза не зависит, но неотслеживаемые служебные папки вроде `.venv/`
   и `dist/` в список попадать не должны — они и не попадают, они в
   `.gitignore`.

### 2.3. Сборка

6. `.venv/Scripts/python.exe build_exe.py` → `dist/QuestLog.exe`.
7. Посчитать хеш и сохранить его в текст релиза:

   ```
   powershell -c "Get-FileHash dist\QuestLog.exe -Algorithm SHA256"
   ```

   Файл не подписан, Windows SmartScreen ругается на любой новый
   незнакомый `.exe`. Хеш в описании релиза — единственное, чем
   человек может проверить, что скачал именно то, что выложили.

### 2.4. Проверка собранного файла

Собранная программа — это отдельно проверяемая вещь: статика внутри
`.exe` запечена на момент сборки и после правок интерфейса не меняется.

8. Запустить `dist/QuestLog.exe` с отдельной папкой профиля, чтобы не
   задеть рабочие данные:

   ```
   USERPROFILE="C:\\Temp\\ql-check" dist/QuestLog.exe --hidden
   ```

9. Проверить, что номер версии виден и статика свежая:
   `curl http://127.0.0.1:8420/api/health` → `"version": "1.0.1"`, и в
   `/static/style.css` находятся последние правки интерфейса.
10. Открыть приложение и посмотреть глазами: вкладки, переименование
    документа, уведомление. Снять процесс и удалить временную папку.

### 2.5. Публикация

11. Закоммитить поднятие версии и отправить ветку:
    `git push origin master`.
    Основная ветка — `master`. Если история не переписывалась после
    прошлого пуша, это обычный fast-forward; `--force` не нужен и
    применять его не стоит.
12. Создать релиз: Releases → Draft a new release → выбрать или создать
    тег `v1.0.1` на текущем `master` → заголовок `QuestLog 1.0.1` →
    описание: что изменилось, прямая ссылка на `QuestLog.exe`, хеш
    SHA-256, предупреждение про SmartScreen.
13. **Опубликовать релиз.** Пока он в черновиках, приложение его не
    увидит: `/api/update` спрашивает `/releases/latest`, а туда попадают
    только опубликованные релизы без пометки pre-release.
14. Приложить `dist/QuestLog.exe` к релизу как asset. В git его класть
    не надо: 22 МБ двоичника в истории не удаляются без переписывания
    всей истории, а пользы не несут.

### 2.6. Проверка, что обновление видно

15. На машине, где ещё не было проверки (или спустя 6 часов — столько
    живёт кэш ответа), открыть `/api/update`:

    ```
    curl http://127.0.0.1:8420/api/update
    {"current":"1.0.0","latest":"1.0.1","available":true,"url":"https://github.com/…/releases/tag/v1.0.1"}
    ```

    `available: true` означает, что подсказка в подвале появится.
    Поле `error` — если проверка не сработала: `403 rate limit exceeded`
    это не поломка релиза, а лимит GitHub (60 запросов в час с адреса
    без ключа API). При таком ответе приложение молча остаётся на текущей
    версии — так и задумано.

## 3. Частые грабли

| Что случится | Почему | Что делать |
|---|---|---|
| Релиз есть, а подсказки в подвале нет | релиз остался в черновиках или помечен как pre-release | опубликовать релиз, снять галочку pre-release |
| Подсказка предлагает обновиться на ту же версию | тег и `VERSION` разошлись | держать тег `v` + содержимое `VERSION` |
| В `.exe` старый интерфейс | статика запечена при сборке | пересобрать `build_exe.py` и перезалить asset |
| В подвале пустая версия | файл `VERSION` не попал в данные сборки | сейчас он добавляется; проверить `/api/health` у собранного файла |
| В репозитории появился `QuestLog.spec` | артефакт PyInstaller | он в `.gitignore`, коммитить не нужно |
| Приложение советует скачать релиз форка | при сборке задан `QUESTLOG_UPDATE_REPO` | собирать релиз без этой переменной |

## 4. Шпаргалка: весь релиз одной строкой

```
python release.py 1.0.1
```

За этим внутри: `VERSION` → тесты и `check_js.py` → `build_exe.py` →
проверка, что `VERSION` попал внутрь сборки → текст релиза с SHA-256 →
коммит и push → тег `v1.0.1` и его push → релиз на GitHub с файлом.

Вручную, если CI недоступен:

```
VERSION=1.0.1 → pytest → check_js.py → build_exe.py → Get-FileHash →
проверить /api/health у собранного .exe → commit → push origin master →
tag v1.0.1 → push origin v1.0.1 → дождаться workflow «Релиз» →
проверить /api/update
```

## 5. Вспомогательные скрипты

| Скрипт | Что делает |
|---|---|
| `release.py` | весь выпуск по одному запуску; без токена доводит до тега, дальше релиз публикует CI |
| `scripts/release_notes.py` | текст релиза: версия, ссылка на файл, размер, SHA-256 |
| `scripts/verify_build.py` | читает готовый `.exe` как архив: версия внутри совпадает с `VERSION`, статика свежая |
| `scripts/check_release_tag.py` | падает, если тег и `VERSION` расходятся |
| `scripts/console_out.py` | UTF-8 в вывод скриптов, иначе русский текст роняет их на Windows |
| `scripts/setup_ruleset.py` | запрет force push в `master` + обязательные проверки |
| `build_exe.py` | сама сборка `.exe` |
| `check_js.py` | синтаксис всех JS-модулей |
